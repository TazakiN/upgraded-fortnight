\subsection{Analisis Sistem DecMed}
\label{subsec:analisis-sistem-decmed}

Sebagaimana dijelaskan pada Bab \ref{sec:decmed}, DecMed adalah kerangka kerja manajemen RME terdesentralisasi dengan menggunakan DLT IOTA sebagai penyimpanan \textit{on-chain}, IPFS sebagai penyimpanan \textit{off-chain}, serta PRE untuk mendukung distribusi akses data yang aman. Arsitektur ini sudah memberikan fondasi untuk menjaga integritas data dan mengurangi ketergantungan pada penyimpanan terpusat. Terdapat tiga aktor utama pada DecMed, yaitu:

\begin{enumerate}
    \item Pasien
    \item Tenaga kesehatan, yang mencakup dokter, petugas administrasi, dan administrator fasilitas pelayanan kesehatan
    \item Pemerintah
\end{enumerate}

Pada DecMed, masing-masing aktor memiliki kepentingan dan aplikasi \textit{client} yang berbeda. \textit{Patient Client} digunakan oleh pasien, \textit{Hospital Client} digunakan oleh tenaga kesehatan di sebuah fasyankes, dan \textit{Ministry Client} digunakan oleh pemerintah. Detail kebutuhan fungsional dari masing-masing aktor dapat dilihat pada Lampiran \ref{lampiran:kebutuhan-fungsional-decmed}.

% ===============================================
% = Masalah Token Kapabilitas
% ===============================================

Model kontrol akses yang digunakan pada sistem DecMed adalah model CapBAC. DecMed memanfaatkan token otorisasi berupa JWT sebagai pembawa bukti otorisasi akses. Ketika pasien ingin mendelegasikan akses ke beberapa tenaga medis, pasien melakukan penerbitan ulang token kepada setiap tenaga medis yang terlibat. Token yang diterbitkan oleh pasien membawa tiga informasi utama, yaitu:

\begin{enumerate}
    \item \textit{Address} IOTA pemegang token
    \item \textit{Role} (bernilai \texttt{AdministrativePersonnel} atau \texttt{MedicalPersonnel})
    \item \textit{Purpose} (bernilai \texttt{Read} atau \texttt{Update})
\end{enumerate}

Pendekatan ini menimbulkan keterbatasan karena token JWT pada DecMed masih bersifat \textit{coarse-grained}. Penentuan hak akses pengguna dilakukan hanya berdasarkan \textit{role} dan \textit{purpose} yang ada pada token yang disertakan saat melakukan \textit{request} ke PRE. Token tersebut belum dirancang untuk membawa batasan kontekstual, misalnya jenis data yang boleh diakses, aksi yang diizinkan, atau batasan delegasi akses. Padahal, pada praktik pelayanan kesehatan, setiap tenaga medis tidak selalu membutuhkan keseluruhan isi RME pasien sesuai dengan prinsip \textit{need-to-know}.
Kondisi ini menunjukkan bahwa mekanisme kontrol akses pada DecMed belum cukup untuk menjawab kebutuhan kontrol akses granular.

% ===============================================
% = Masalah Delegasi Akses
% ===============================================

Selain kontrol akses granular, alur layanan kesehatan kolaboratif juga menimbulkan kebutuhan delegasi akses yang fleksibel antartenaga medis. Kebutuhan ini dibahas lebih lanjut melalui skenario layanan kesehatan kolaboratif pada Subbab \ref{subsubsec:analisis-skenario-layanan-klinis}.

% ===============================================
% = Masalah Segmentasi Data Klinis
% ===============================================

Data klinis pada DecMed disimpan dalam dua sistem penyimpanan yang berbeda, yaitu penyimpanan \textit{on-chain} dan \textit{off-chain}. Penyimpanan \textit{on-chain} digunakan untuk menyimpan metadata klinis dan CID dari data klinis yang disimpan di \textit{off-chain}. Penyimpanan \textit{off-chain} digunakan untuk menyimpan data administratif dan klinis yang sudah terenkripsi. Pemisahan ini sesuai dengan kebutuhan yang dibahas pada \ref{subsec:isi-rme} terkait bagian administratif dan klinis.

Pada penyimpanan \textit{on-chain}, data klinis pasien direpresentasikan sebagai metadata. Metadata tersebut menyimpan CID serta informasi kunci yang dibutuhkan pasien untuk mendekripsi data medis terkait. Struktur penyimpanannya terikat dengan \textit{struct} \texttt{PatientAccount} dan \texttt{PatientMedicalMetadata} berikut:

\begin{lstlisting}[language=Move]
public struct PatientAccount has store {
    ...
    medical_metadata: TableVec<PatientMedicalMetadata>,
}
public struct PatientMedicalMetadata has copy, drop, store {
    index: u64,
    metadata: String,
}
\end{lstlisting}

Variabel \texttt{metadata} pada \textit{struct} \texttt{PatientMedicalMetadata} merupakan serialisasi dari \textit{struct} berikut:

\begin{lstlisting}[language=Rust]
#[derive(Debug, Deserialize, Serialize)]
pub struct MedicalMetadata {
    pub capsule: String, // capsule untuk PRE re-encryption
    pub cid: String, // pointer ke data di IPFS
    pub created_at: String, // timestamp
    pub enc_key_and_nonce: String, // kunci dan nonce yang terenkripsi
}
\end{lstlisting}

\texttt{cid} pada \textit{struct} \texttt{MedicalMetadata} merupakan \textit{pointer} ke data klinis yang sudah terenkripsi disimpan di penyimpanan \textit{off-chain} sebagai sebuah \textit{Encrypted Blob}. Potongan field relevan pada \textit{struct} \texttt{MedicalData} dapat dilihat berikut:

\begin{lstlisting}[language=Rust]
pub struct MedicalData {
    pub anamnesis: String,
    pub physical_check: String,
    pub psychological_check: String,
    pub diagnose: String,
    pub therapy: String,
}
\end{lstlisting}

Penyimpanan data klinis pada DecMed hanya berfokus pada dataset rawat jalan, sesuai dengan ketentuan pada KMK No. HK.01.07/Menkes/1423/2022 \autocite{kemenkes1423-2022} tentang Pedoman Variabel dan Metadata Rekam Medis terkait data klinis rawat jalan. Pada \textit{struct} \texttt{MedicalData}, data klinis masih disimpan dengan format yang sederhana, tanpa kategorisasi yang jelas. Hal ini berkaitan dengan organisasi data pada lapisan \textit{off-chain}. DecMed memang telah memisahkan penyimpanan \textit{on-chain} dan \textit{off-chain}, tetapi pendekatan tersebut belum secara eksplisit menunjukkan segmentasi data klinis yang cukup rinci untuk menegakkan kebijakan akses granular. Jika data klinis masih dikelola sebagai objek terenkripsi yang terlalu besar, pemberian akses kepada tenaga medis berisiko membuka data di luar kebutuhan klinisnya.
