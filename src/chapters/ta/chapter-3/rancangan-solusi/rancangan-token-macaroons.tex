\subsection{Rancangan Token Otorisasi Berbasis Macaroons}
\label{subsec:rancangan-token-macaroons}

Macaroons digunakan sebagai pengganti token kapabilitas DecMed yang sebelumnya bersifat \textit{coarse-grained}. Token Macaroon tetap mengikuti model CapBAC karena token berperan sebagai bukti kapabilitas yang dibawa oleh pemegang akses. Perbedaannya, Macaroon dapat menyimpan batasan kontekstual dalam bentuk \textit{caveats} dan dapat diatenuasi secara lokal oleh pemegang token tanpa memerlukan penerbitan ulang token oleh \textit{Server} PRE.

Pada rancangan ini, \textit{Server} PRE bertindak sebagai \textit{issuer} token Macaroon awal dan memegang \texttt{RootKey} yang digunakan untuk proses penandatanganan token. \texttt{RootKey} disimpan pada \textit{environment variable} \textit{Server} PRE dan tidak pernah diberikan kepada \textit{client}. Token awal diterbitkan oleh \textit{Server} PRE setelah terdapat persetujuan dari pasien sebagai pemilik data. Dengan demikian, sifat \textit{patient-centric} tetap dipertahankan karena penerbitan akses awal tetap bergantung pada persetujuan pasien, sedangkan otoritas kriptografis penerbitan token berada pada \textit{Server} PRE.

Setelah token awal diterbitkan, pemegang token dapat melakukan atenuasi secara lokal dengan menambahkan \textit{caveat} baru pada token yang dimilikinya. Atenuasi lokal ini memungkinkan, misalnya, dokter yang memiliki token akses dari pasien untuk membuat token turunan dengan cakupan lebih sempit bagi petugas laboratorium atau petugas apotek. Token turunan tersebut tidak memerlukan \texttt{RootKey}, karena proses penurunan Macaroon dilakukan dengan menambahkan \textit{caveat} baru pada token induk. \textit{Server} PRE hanya berperan sebagai pihak yang memverifikasi token ketika token digunakan untuk meminta akses atau proses \textit{re-encryption} terhadap data.

Karena Macaroon bersifat \textit{append-only}, \textit{caveat} pada token induk tidak dapat dihapus atau diganti pada token turunan. Oleh karena itu, rancangan \textit{caveat} harus dibuat dalam bentuk batasan yang bersifat monoton, yaitu setiap \textit{caveat} baru hanya dapat mempersempit hak akses dan tidak dapat memperluas hak akses. Dengan demikian, token turunan yang dibuat oleh \textit{client} tetap aman karena seluruh batasan pada token induk tetap ikut terbawa dan diverifikasi oleh \textit{Server} PRE.

Pada rancangan ini, \textit{caveat} \texttt{holder\_address} tidak digunakan sebagai penanda pemegang token saat ini. Hal ini disebabkan karena nilai pemegang token akan berubah ketika token didelegasikan, sedangkan Macaroon tidak mendukung penghapusan atau penggantian \textit{caveat} lama. Apabila token induk memiliki \texttt{holder\_address = 0xDOKTER} dan token turunan menambahkan \texttt{holder\_address = 0xLAB}, maka token tersebut akan memiliki dua batasan identitas yang harus dipenuhi secara bersamaan. Kondisi tersebut dapat menyebabkan token tidak dapat digunakan karena satu permintaan akses tidak mungkin berasal dari dua alamat pemegang yang berbeda.

Sebagai gantinya, rancangan ini menggunakan pendekatan rantai delegasi dengan \textit{caveat} \texttt{root\_subject}, \texttt{delegated\_by}, dan \texttt{delegated\_to}. \texttt{root\_subject} menyatakan aktor penerima token awal dari pasien, sedangkan \texttt{delegated\_by} dan \texttt{delegated\_to} digunakan untuk merepresentasikan proses delegasi pada token turunan. Dengan pendekatan ini, aplikasi \textit{client} dapat menambahkan informasi delegasi baru tanpa perlu mengubah \textit{caveat} yang sudah ada sebelumnya.

Selain informasi delegasi, token juga memuat batasan akses terhadap data RME tertentu. \textit{Caveat} \texttt{patient\_address} digunakan untuk mengikat token terhadap data RME milik pasien tertentu. \textit{Caveat} \texttt{related\_rme\_id} digunakan untuk membatasi token terhadap satu episode pelayanan atau data RME tertentu. Kedua \textit{caveat} tersebut memastikan bahwa token tidak dapat digunakan untuk mengakses data pasien lain atau episode pelayanan lain yang tidak termasuk dalam cakupan token.

Mekanisme pembatasan kategori data dilakukan dengan metode \textit{whitelisting}. Token harus secara eksplisit menyatakan kategori data dan kategori fungsi yang dapat diakses oleh pemegang token. Rancangan ini menggunakan \textit{caveat} \texttt{read\_dataset\_in}, \texttt{write\_dataset\_in}, \texttt{read\_function\_in}, dan \texttt{write\_function\_in}. Keempat \textit{caveat} tersebut disesuaikan dengan metadata segmen RME yang disimpan secara \textit{on-chain}, khususnya atribut \texttt{dataset\_category} dan \texttt{function\_category}. Dengan demikian, \textit{Server} PRE dapat memvalidasi apakah segmen yang diminta termasuk dalam cakupan akses yang diizinkan oleh token.

Pembatasan waktu akses dilakukan dengan \textit{caveat} \texttt{expires\_before}. \textit{Caveat} ini menyatakan batas waktu maksimum token dapat digunakan. Pada token turunan, nilai \texttt{expires\_before} harus sama dengan atau lebih awal daripada token induk. Dengan demikian, pemegang token tidak dapat memperpanjang masa berlaku akses melalui proses delegasi.

Pembatasan jumlah delegasi dilakukan dengan \textit{caveat} \texttt{max\_delegation\_depth}. Nilai ini menyatakan jumlah maksimum delegasi yang masih diperbolehkan dari token terkait. Token awal dapat memiliki nilai \texttt{max\_delegation\_depth = 1} apabila penerima token diperbolehkan membuat satu token turunan. Token turunan kemudian dapat menambahkan \textit{caveat} \texttt{max\_delegation\_depth = 0} agar token tersebut tidak dapat didelegasikan lebih lanjut.

Agar token tidak dapat digunakan oleh pihak yang hanya memperoleh salinan token tanpa memiliki identitas kriptografis yang sesuai, setiap permintaan akses harus disertai bukti kepemilikan alamat \textit{wallet}. Bukti tersebut direpresentasikan dengan \textit{caveat} \texttt{proof\_required = wallet\_signature}. Pada saat token digunakan, pemohon akses harus menandatangani konteks permintaan menggunakan kunci privat dari alamat yang menjadi subjek aktif pada rantai delegasi. \textit{Server} PRE kemudian memverifikasi tanda tangan tersebut sebelum memproses permintaan akses.

Sebagai contoh, pasien dapat memberikan token awal kepada dokter dengan cakupan akses yang luas untuk satu episode pelayanan tertentu. Token tersebut dapat berisi \textit{caveat} sebagai berikut.

\begin{lstlisting}[caption={Contoh Caveat Token Awal untuk Dokter}, label={lst:contoh-token-awal-dokter}]
patient_address = 0xPASIEN
related_rme_id = RME-001
root_subject = 0xDOKTER

read_dataset_in = [RAWAT_JALAN, RAWAT_INAP, LABORATORIUM, APOTEK]
write_dataset_in = [RAWAT_JALAN, RAWAT_INAP, LABORATORIUM, APOTEK]

read_function_in = [
  ANAMNESIS,
  PEMERIKSAAN_FISIK,
  DIAGNOSIS,
  TERAPI,
  PERMINTAAN_PEMERIKSAAN,
  HASIL_PEMERIKSAAN,
  DATA_RESEP_DAN_OBAT
  ...
]

write_function_in = [
  ANAMNESIS,
  PEMERIKSAAN_FISIK,
  DIAGNOSIS,
  TERAPI,
  PERMINTAAN_PEMERIKSAAN
  ...
]

expires_before = 2026-05-16T18:00:00
max_delegation_depth = 1
\end{lstlisting}

Nilai \texttt{0xPASIEN}, \texttt{RME-001}, \texttt{0xDOKTER}, dan \texttt{0xLAB} adalah contoh nilai yang hanya bersifat ilustratif. Pada kenyataannya, nilai pemegang token akan berbeda-beda tergantung pada alamat \textit{wallet} yang digunakan dan ID RME yang di-\textit{generate}. Simbol titik tiga (\texttt{...}) adalah bentuk ilustrasi yang digunakan untuk menunjukkan bahwa token dapat memiliki lebih banyak nilai lainnya selain yang dituliskan di sini.

Pada saat token turunan digunakan oleh petugas laboratorium, \textit{Server} PRE akan memverifikasi seluruh \textit{caveat} yang terdapat pada token, baik \textit{caveat} dari token awal maupun \textit{caveat} tambahan dari token turunan. Mekanisme verifikasi token pada \textit{Server} PRE dijelaskan pada Subbab \ref{subsec:rancangan-penegakan-otoritas-pada-PRE}.

Dengan rancangan tersebut, Macaroon tetap digunakan sesuai karakteristik utamanya, yaitu memungkinkan atenuasi token secara lokal. \textit{Server} PRE tidak perlu menerbitkan ulang token turunan, melainkan hanya memverifikasi token ketika digunakan. Token turunan juga tidak dapat memperluas hak akses karena seluruh \textit{caveat} pada token induk tetap ikut terbawa. Oleh karena itu, setiap delegasi hanya dapat menghasilkan hak akses yang sama atau lebih sempit dibandingkan token induknya.

Rancangan ini juga mendukung prinsip \textit{least privilege}. Dokter dapat memiliki cakupan akses yang relatif luas untuk menjalankan tugas klinisnya, tetapi token turunan yang diberikan kepada petugas laboratorium atau petugas apotek dapat dibatasi hanya pada segmen yang relevan. Sebagai contoh, petugas laboratorium hanya dapat membaca segmen \texttt{PEMERIKSAAN\_PENUNJANG} pada \textit{dataset} \texttt{RAWAT\_JALAN} dan menulis segmen \texttt{LABORATORIUM} pada \textit{dataset} \texttt{LABORATORIUM}. Petugas tersebut tidak dapat membaca diagnosis, anamnesis, resep, atau segmen klinis lain yang tidak termasuk dalam \textit{caveat} token turunannya.
